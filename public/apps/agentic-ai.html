Module 01

AI & LLM Foundations

Everything an agent is built on: a Large Language Model that turns text into tokens, maps tokens into embedding vectors, and uses attention to decide which tokens matter. Play with each primitive below.

🧠LLM

A neural network trained to predict the next token. Given "The cat sat on the…", it assigns probabilities to every possible next token and samples one.

🔤Tokens

The atomic units of text (≈4 chars). Models see token IDs, not words. Context windows are priced and limited in tokens.

📍Embeddings

Numbers-in-space representation of meaning. Similar meanings → nearby vectors. Powers search, RAG and memory.

🎯Attention

Each token computes a weighted look at every other token. This is how "it" knows what "it" refers to.

How Models Learn — ML Paradigms

Three families of learning power everything from spam filters to autonomous agents. The animated chart shows a reinforcement-learning agent actually improving episode after episode.

🏷️Supervised

Learn input→output from labeled pairs. Example: classify tickets as bug/feature. LLM pre-training & fine-tuning are supervised next-token prediction at massive scale.

Find structure with no labels: clustering, embeddings, dimensionality reduction. This is what produces the embedding space in Module 01 and powers semantic search.

An agent acts in an environment, receives reward, and optimizes long-term return. RLHF/RLAIF uses this to align LLMs; agents use it to learn tool policies.

Module 03

AI Agents — the ReAct Loop

An agent = LLM + a loop: it perceives a goal, thinks (reasons), acts (calls a tool), observes the result, and repeats until done. Press run and watch a real trace unfold step-by-step.

🔄The Agent Loop

agent.py — the whole idea in 10 lines
# Minimal ReAct agent loop
def run_agent(task, tools, llm, max_steps=8):
    history = [{"role": "user", "content": task}]
    for step in range(max_steps):
        reply = llm.chat(history, tools=tools)   # THINK
        if reply.tool_call:                      # ACT
            out = tools[reply.tool_call.name](**reply.tool_call.args)
            history.append({"role": "tool", "content": out})  # OBSERVE
        else:
            return reply.content                 # FINAL ANSWER
    return "max steps reached"

Module 04

Superpowers: Tools, Function-Calling & Memory

A bare LLM can only talk. Tools let it do; memory lets it remember. Function-calling is the contract: you describe a function with JSON Schema, the model emits structured arguments, your runtime executes it.

🛠Function Calling Flow

1 · User
"What's the weather in Tokyo?"
➜
2 · LLM chooses tool
emits {"name":"get_weather","arguments":{"city":"Tokyo"}}
➜
3 · Your runtime executes
runs real code / API, returns result string to the model
tool_schema.json
{
  "name": "get_weather",
  "description": "Get current weather for a city",
  "parameters": {
    "type": "object",
    "properties": {
      "city":  { "type": "string", "description": "City name" },
      "units": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["city"]
  }
}

💾Memory Playground

Long-term memory = memories embedded into a vector store, retrieved by similarity when relevant. Store a memory, then query the store — retrieval uses keyword-overlap scoring as a stand-in for cosine similarity.

chunks = split_docs(docs, size=400, overlap=80)
index  = embed(chunks)                    # → vector DB

def answer(question):
    hits = index.search(embed(question), top_k=3)
    ctx  = "\n".join(h.text for h in hits)
    return llm.chat(f"Context:\n{ctx}\n\nQ: {question}")

Module 07

MCP — Model Context Protocol

MCP is an open standard (JSON-RPC 2.0) that gives AI applications a universal plug for tools and data — the "USB-C of AI". Instead of M×N custom integrations, every app speaks MCP to every server. Servers expose three primitives: Tools (callable functions), Resources (readable data) and Prompts (reusable templates).

🛠Tools

Model-controlled actions: search_files, create_issue, run_query. Discovered via tools/list, invoked via tools/call.

📚Resources

App-controlled context: file contents, DB rows, tickets. Read via URI-like identifiers (file:///src/app.py) without executing anything.

📝Prompts

User-controlled templates served by the server, e.g. /debug-error with arguments — shareable, versioned prompt engineering.

🏗️Architecture: Host → Clients → Servers

The host (your AI app/IDE) spawns one MCP client per connection. Each client keeps a 1:1 stateful session with a server over stdio or HTTP+SSE. Packets below animate the JSON-RPC traffic.

🐍Build a Server in 12 Lines

weather_server.py
# MCP server with the official Python SDK
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """Get current weather for a city."""
    return f"{city}: 28°C, partly cloudy"

if __name__ == "__main__":
    mcp.run(transport="stdio")

⚖️MCP vs Function Calling

Function calling is a per-model feature: schemas live in your app code. MCP is a per-ecosystem protocol: schemas live in the server, are discovered at runtime, and work identically across every MCP-capable host. Use function calling for in-app tools; use MCP to share tools across apps, teams and products.
